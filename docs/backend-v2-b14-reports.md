# B14 — единые отчёты и повторяющиеся проблемы

## Что добавлено

Новый отчёт объединяет спроецированные сигналы Collector, Zabbix и Prometheus через связанные инциденты B12 и текущие подтверждённые связи с Asset. Отбор: период, Asset, физическая площадка, real/simulated/all. По умолчанию последние 24 часа и только реальные наблюдения. Период от одной секунды до 31 дня; списки ограничены 200 строками, обрезка явно обозначается.

Числа отражают разные сущности: distinct связанные инциденты, distinct сигналы и затронутые Assets. Один инцидент с несколькими источниками не становится несколькими эпизодами. Повторяющаяся проблема — минимум три разных связанных инцидента, открытых за выбранный период для одного Asset и категории. Реальные и симулированные наблюдения разделены; simulation namespace включает Collector. Категории и rule_ids позволяют отличать производительность, аппаратные симптомы, SIP, события конфигурации, topology и logs.

Суммарная продолжительность обрезана границами периода и вычисляется по записанному lifecycle. Она может пересекаться между инцидентами и **не является измеренным простоем или процентом доступности**. Отсутствие инцидентов не доказывает здоровье оборудования. Размещение, bindings и сервисные зависимости берутся текущие, подтверждённые; прошлое размещение не реконструируется. Ещё не спроецированные данные не входят в числа; глобальное число ожидающих обработки записей показано отдельно. Статус подключения источника — текущая сохранённая информация, не исторический uptime.

## REST для frontend

- GET `/api/reports/v2/summary`: `from`, `to` RFC3339, `asset_id`, `site_id`, `scope`, `limit`.
- POST `/api/reports/v2/snapshots`: JSON фильтра и обязательный `Idempotency-Key`; operator/admin, при cookie нужен CSRF. Повтор возвращает тот же неизменяемый снимок, другой фильтр с тем же ключом даёт конфликт.
- GET `/api/reports/v2/snapshots` и GET `/api/reports/v2/snapshots/{id}`: чтение сохранённых снимков.
- GET/POST `/api/reports/schedules`, PUT `/api/reports/schedules/{id}`: только admin. Создание требует `confirmed=true`, reason и cadence daily/weekly; изменение требует expected_revision.

Старые `/api/reports/summary` и `/api/reports/snapshots` сохранены. Legacy и unified снимки разделены по kind, старые маршруты не возвращают новую несовместимую JSON структуру. Контракт находится в `internal/api/openapi.json` и доступен через GET `/openapi.json`, версия 0.44.0.

## Расписание

Ежедневный отчёт охватывает последний завершённый календарный день UTC. Еженедельный — последнюю завершённую неделю UTC, понедельник–понедельник. После создания первое выполнение готовит последний завершённый период; далее следующий запуск назначается на календарную границу. После простоя создаётся последний завершённый период, а не выдуманные исторические снимки за все пропущенные дни.

Worker проверяет очередь раз в минуту и выполняет одно расписание за проход. До 20 расписаний на владельца; имя уникально внутри владельца без учёта регистра. Повтор POST с тем же именем даёт 409: следует обновить список, а не создавать вторую политику. Создание расписания — явное долговременное разрешение администратора; logout его не отменяет. Каждый запуск повторно проверяет актуальную роль/disabled владельца; отзыв доступа отключает расписание с owner_access_revoked. Недоступный Asset/site отключает его с scope_unavailable. События управления и выполнения записываются в аудит.

Снимок, запись выполнения периода и переход next_run_at сохраняются одной транзакцией. Ошибка откатывает все три изменения; запись остаётся для следующей попытки. Блокировки и уникальный ключ периода предотвращают два снимка одного расписания/ревизии/периода. Это внутренние отчёты: писем и внешних уведомлений worker не отправляет.

## Хранение и проверки

Новые миграции 044 и 045 добавляют kind снимка и таблицы расписаний/ревизий/выполнений. Старые опубликованные миграции не переписаны. Summary читает согласованный repeatable-read снимок PostgreSQL с ограниченным временем запроса.

Проверены три последовательных эпизода с восстановлением, chronic count, фильтр площадки с иерархией site/building/room, идемпотентный снимок, отделение legacy JSON, генерация расписания без дубля и отзыв роли владельца. HTTP тесты проверяют admin/operator/viewer, cookie CSRF и отказ от неизвестных JSON полей. Проверка на реальных источниках команды и оценка нагрузки на её объёме остаются частью итоговой приёмки B16.
