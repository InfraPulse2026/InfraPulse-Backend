# Этап 3: поиск по логам и Linux audit

Этот этап закрывает пункт 2 присланного списка. Backend подготовлен локально,
GitHub пока не обновлён. ZIP содержит также этап 1 (topology) и этап 2
(доступность и expiry). Исходники Agent и wire-контракт не изменены.

## Что было во вчерашней версии

Backend уже принимал `LogBatch` через существующий gRPC stream и сохранял
envelope в `agent_messages`. Вложенные `AuditRecord` не терялись, но искать их
через отдельный API было нельзя. Теперь архив остаётся, а параллельно создаются
нормализованные строки с индексами и понятными frontend полями.

## Как данные проходят по шагам

1. Agent читает настроенный источник логов, разбирает syslog/auditd и отправляет
   обычный `LogBatch`. Код Agent менять не требуется.
2. Controller проверяет envelope и размер/времена/идентичность строк.
   Пустой пакет допустим; верхняя граница — 1024 строки, как у текущего Agent.
3. В одной транзакции сохраняются архив, запись пакета, строки логов и audit.
   Неизвестное устройство получает минимальную карточку с ID. Лог сам по себе
   не делает устройство online и не обновляет inventory существующего устройства.
4. Только после COMMIT Controller возвращает application ACK, если поддержка
   согласована с Agent. Ошибка SQL или конфликт ID откатывает весь пакет.
5. REST API читает готовые поисковые таблицы. Он не обращается к файлам Agent
   и не разбирает заново весь архив на каждый запрос.

Миграция `006_logbook.sql` добавляет `log_batches`, `log_records`, `audit_records`.
Миграции опубликованной основы 001..003 не переписываются. При обычном старте
backend применяет ещё не выполненные миграции автоматически.

## Поля строки и время события

`id` — числовой ID строки в backend; `record_id` — ID, присланный Agent.
Сохраняются Agent/device, source/source_id, host/process/process_id,
message/raw, file_identity/offset, severity/facility, признаки усечения и
маскирования. Вложенный `audit` содержит event ID/type, UID/AUID/PID,
executable, syscall и success/result; у обычной строки это `null`.

- `original_timestamp` — дата события в исходном логе, если Agent смог её разобрать.
- `observed_at` — время сбора; при отсутствии в строке используется время пакета,
  затем envelope.
- `received_at` — время приёма backend.
- `event_at` — original_timestamp, иначе observed_at. `time_basis` объясняет выбор.

Фильтры `from`/`to` работают по `event_at`. Поэтому старое событие, доставленное
сейчас, остаётся событием старого периода. Будущая дата сохраняется как
полученный факт, не становится доказательством здоровья устройства.

Неизвестный severity/UID/success остаётся `null`, а `0` и `false` сохраняются
как реальные переданные значения. Неизвестный severity имеет имя `unknown`;
0..7 отображаются как emergency/alert/critical/error/warning/notice/info/debug.
Результат audit `false` означает сообщённую неуспешную операцию, не обязательно
инцидент безопасности: диагноз остаётся следующим этапом.

## REST API для frontend

| Путь GET | Назначение |
|---|---|
| `/api/logs` | Поиск и список всех строк |
| `/api/logs/{id}` | Одна строка по backend ID |
| `/api/logs/summary` | Число строк/audit failures, severity, redacted/truncated |
| `/api/audit` | Только строки с AuditRecord |
| `/api/audit/events` | Группы строк одного audit события |
| `/api/audit/events/{key}` | Строки выбранной группы |
| `/api/devices/{id}/logs` | Логи одного устройства |
| `/api/devices/{id}/audit` | Аудит одного устройства |

Точные строковые фильтры: `agent_id`, `device_id`, `source`, `source_id`,
`host`, `process`, `record_type`, `event_id`, `executable`.
Числовые: `severity=0..7`, `facility`, `uid`, `auid`, `pid`.
Есть `severity=unknown`, `success=true|false|unknown`.
Числа допускают uint32; `success=unknown` выбирает audit с неизвестным результатом,
а не все обычные логи. При неоднозначном device ID нужен `agent_id`, иначе 409.

`q=denied` использует встроенный полнотекстовый поиск PostgreSQL `simple` и GIN
индекс. Он ищет слова, поддерживает фразы, не является произвольным regexp или
поиском любого фрагмента слова. Текст поиска включает очищенные message/raw,
host/process и executable/syscall/result. SQL строится с параметрами.
Дополнительные расширения PostgreSQL устанавливать не нужно.

Для фрагмента слова есть `contains=den`: поиск буквальной подстроки без учёта
регистра. Для него обязательны `from` и `to`, окно не более семи суток;
такой поиск не использует полнотекстовый индекс. `q` и `contains` нельзя смешивать.
Строковые фильтры ограничены 256 UTF-8 байтами. `from` включительно, `to`
исключительно, формат RFC3339 с часовым поясом. Неверные параметры дают 400.

Примеры в браузере при запущенном backend:

```text
http://127.0.0.1:8080/api/logs?q=denied&limit=100
http://127.0.0.1:8080/api/audit?success=false&uid=1000
http://127.0.0.1:8080/api/audit/events?record_type=SYSCALL
http://127.0.0.1:8080/api/logs/summary?severity=error
```

Для страницы используется `limit` 1..500, по умолчанию 100.
Ответ: `{"items":[...],"next_before_id":42,"limit":100}`.
Передайте следующий `before_id=42`, сохранив остальные фильтры. `null` означает,
что в этом ответе продолжения нет; пустой список — `[]`. Числовые ID идут по
убыванию порядка вставки, а не даты исходного события. `offset` здесь не нужен.
Сводка считает все совпадения, игнорируя пагинацию.

Это не зафиксированный снимок всей базы: новые записи могут поступать между
запросами. Audit группы при поступлении дополнительных строк могут переместиться
в начало списка. Для живого экрана обновляйте первую страницу; для просмотра
прошлого задавайте период. OpenAPI 0.5.0 описывает маршруты и DTO.

## Как группируется audit

Linux audit может описывать одну операцию несколькими строками `SYSCALL`, `PATH`,
`CWD`, `EXECVE`. Одинаковый `event_id` не повод выбрасывать остальные строки.
Они сохраняются отдельно; `event_key` связывает их внутри Agent/device/source,
source_id, file_identity и host. Для Simulator добавляется session scope,
чтобы повтор сценария не смешивался с предыдущим запуском.
При пустом event ID записи остаются отдельными группами.

Группа показывает число найденных строк, record_types и outcome:
success/failure/mixed/unknown. Фильтры действуют до группировки: например,
`uid=1000` считает только соответствующие строки, не всю операцию.
`completeness` всегда `unknown`: текущий контракт не доказывает, что все строки
операции дошли. Наличие одной строки не выдаётся за полностью восстановленный
audit event. Это Linux audit, а журнал действий пользователей backend появится
вместе с auth/commands.

## Повторная доставка и перечитывание файла

Уникальность envelope остаётся `(agent_id,message_id)`. Переподключение с новым
sequence/sent_at не повторяет domain effect принятого сообщения.
Для строки дополнительно используются Agent/device, scope, source/source_id
и record_id. Повтор той же строки в новом пакете не создаёт дубликат.
Collection observed_at исключён из fingerprint: при перечитывании файла он
может измениться. Исходная дата события и остальные business fields учитываются.
Сравнение делается до маскирования; изменение даже скрытого текста под прежним
ID отклоняется. При отсутствии record ID создаётся fallback по message_id/индексу:
надёжно дедуплицировать такую строку между разными пакетами невозможно.

## Как открыть поиск по старым архивным логам

Новые пакеты сразу появляются в API. Старые, записанные вчера, автоматически
не перерабатываются на старте: большой архив не должен задерживать запуск.

После запуска новой версии и применения миграции 006 можно выполнить из корня
backend с тем же `DATABASE_URL`:

```sh
go run ./cmd/backfill-logs -limit 100 -timeout 5m
```

В контейнерном варианте бинарник добавлен в Dockerfile:

```sh
docker compose exec backend /app/backfill-logs -limit 100 -timeout 5m
```

Команда выдаёт JSON с processed_batches/inserted_records/failed_batches.
Повторяйте небольшими порциями до нулевого processed_batches при отсутствии
ошибок. Уже обработанные пакеты пропускаются; отдельная транзакция на пакет
не сбрасывает активные Agent connections и не повторяет telemetry/topology.
Неверные старые записи остаются в архиве, failed_batches сообщается явно,
CLI заканчивается с ошибкой. Такие записи требуют отдельного разбора: при
повторных запусках они могут снова попадать в выборку. Команда их не удаляет.
Она не применяет миграции, поэтому сначала запускается новый backend.

## Безопасность и ограничения

Agent уже умеет фильтровать известные ему секреты. Backend дополнительно
маскирует типовые password/token/community, Bearer/Basic и private key блоки
в текстовых поисковых полях. Эти очищенные значения выдаёт REST и индексирует
поиск. `redacted=true` сообщает о фильтрации.

Это не исчерпывающее обезличивание. IP/hostnames, UID, пути файлов и неизвестные
секреты могут остаться. Исходный envelope в `agent_messages` хранится как
прислан Agent; дополнительная очистка проекции его не переписывает. Нельзя
обещать, что сырой архив безопасен для отправки внешнему ИИ. Export allowlist,
operator audit trail, user auth/roles и retention — следующие отдельные этапы.
API пока development, порты loopback. Полный список из скриншота не закончен.

Для реальных Linux логов владелец Agent должен включить существующие источники
`logs.sources` и проверить права чтения файлов. Пример уже есть в Agent
`configs/config.p2.example.yaml`: syslog и auditd. Копировать отсутствующие на
машине пути вслепую не следует. Код Agent в этом этапе не менялся.

## Что проверено локально

Юнит/API тесты и PostgreSQL integration проверяют null/0/false, индексы поиска,
фильтры, pagination, группы из разных record types, source/Agent/session
изоляцию, перечитывание, конфликт ID, откат SQL ошибки, пакет 260 строк через
несколько порций, архивный backfill и сохранение активной сессии.

Неизменённый Agent P3 Simulator запущен со сценарием audit-activity на 5s,
interval=1s, четырьмя устройствами и текущим UTC start. Backend принял пять
пакетов, создал восемь строк, в том числе три audit failures. REST поиск denied
вернул три строки; фильтр success=false/uid=1000 — три; группировка — три группы.
Две страницы по две строки и подробности группы сохранены в
`docs/examples/logs.*.simulated.json`. Эти данные синтетические, не события
настоящего Linux auditd. Границы проверок описаны в [validation.md](validation.md).
