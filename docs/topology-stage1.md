# Этап 1: карта обнаруженных соседей

Это описание этапа 1 после слияния совместимости Agent P3. В общем ZIP этапа 2 уже добавлено [availability](availability-stage2.md); ограничения ниже относятся к моменту завершения этапа 1.
Agent и protobuf-контракт не изменяются. Реализован пункт topology из списка
доработок платформы. Новый этап не опубликован на GitHub.

## Как проходит сообщение

```text
Agent: TopologyUpdate
  → проверка структуры и дат
  → PostgreSQL: одна транзакция
      agent_messages + topology_snapshots + topology_observations
  → commit
  → MessageACK, если согласован application_ack

Frontend: GET /api/topology
  → согласованный снимок PostgreSQL
  → сопоставление соседей с inventory
  → JSON: nodes + edges + collections
```

До этого topology сохранялась только внутри общего архива envelopes.
Теперь она также представлена отдельными таблицами и доступна через REST.
Полное исходное сообщение продолжает сохраняться.

## Два новых вида данных в PostgreSQL

Миграция `004_topology.sql` добавляет:

- `topology_snapshots`: история опросов, включая complete/partial/failed;
  agent/device/message ID, observed_at, collected_at, received_at, source,
  объявленный TTL, пояснение TTL, число observations и полный payload.
- `topology_observations`: последнее наблюдение каждой направленной связи;
  стабильный edge ID, протокол, источник, время наблюдения, получения и expiry,
  исходный Neighbor с портами, chassis ID и evidence.

Старые миграции 001–003 не переписываются. При запуске новая миграция
применяется автоматически и не удаляет существующие данные.
Сообщения, принятые до миграции 004, остаются в общем архиве. Автоматический
backfill старого архива в новые таблицы в этом этапе не реализован:
карта начнёт наполняться при поступлении новых TopologyUpdate.

## Узлы, связи и идентичность

Известный узел — запись устройства в backend. Его ID строится из пары
`agent_id + device_id`: одинаковые device_id разных collectors не склеиваются.
Если topology пришла до inventory, создаётся минимальная запись устройства;
это не переводит его в online.

Неизвестный сосед остаётся узлом с `known:false`. Для него не создаётся
выдуманная карточка устройства. Повторное наблюдение того же chassis сохраняет
стабильный node ID. При отсутствии chassis идентичность ограничена конкретным
наблюдением/портом, чтобы не объединять соседей с одинаковым именем.

Сопоставление выполняется только среди устройств того Agent, который
прислал наблюдение:

1. LLDP chassis MAC сопоставляется с chassis_id из inventory.
2. LLDP network-address chassis сопоставляется с management_address.
3. Строковый chassis ID сопоставляется с chassis_id.
4. Если сильное сопоставление не найдено, используется уникальный hostname.
   Это предположение средней уверенности, а не доказанная физическая идентичность.

Дубликаты дают `ambiguous`, а противоречие hostname и сравнимого chassis —
`conflicting`. В обоих случаях сосед остаётся отдельным узлом. Кандидаты
возвращаются в `candidate_node_ids`. Подтип 0 RouterOS не подменяется подтипом
LLDP MAC: отсутствие данных не заполняется догадкой.

Поиск использует предварительно построенные индексы идентичности.
MAC/IP/chassis/hostname не приходится повторно перебирать для каждой связи.
Глобальное объединение физических устройств разных Agent в этом этапе отсутствует.

## Что означает линия на карте

`edges` — направленные наблюдения: устройство A сообщило о соседе B
на конкретном локальном порту. LLDP, CDP и MNDP сохраняются отдельно;
параллельные порты не склеиваются. Противоположные наблюдения A→B и B→A
тоже сохраняются отдельно.

Это карта discovery evidence. MNDP и другие наблюдения не гарантируют
прямой физический кабель между узлами. Двустороннее подтверждение кабеля,
схлопывание протоколов и логическая маршрутизация — отдельные будущие задачи.

У связи есть protocol, source, local_port, remote_port, observation_confidence,
resolution и evidence. Исходные двоичные chassis/port ID передаются в base64,
а не превращаются в потенциально неверный текст.

## Срок жизни и неудачные опросы

Время измерения — `observed_at`; время прихода — `received_at`.
Поздняя доставка не обновляет возраст измерения.

- Используется `Neighbor.expires_at`, если он задан.
- Иначе expiry = observed_at + TopologyUpdate.ttl_seconds.
- Если TTL не задан (0), используется явный fallback 900 секунд.
- Максимальный срок — 24 часа, как в текущем Agent.

TTL — допущение collector, не гарантированное время жизни физической связи.
`expiry_assumption` возвращается в информации о сборе.

При чтении API expiry сравнивается с временем backend. В стандартную карту
попадают только активные observations. Истёкшие записи сохраняются для диагностики.
Не нужен новый heartbeat или очередное сообщение, чтобы API перестал показывать
истёкшую связь. Это не означает физическое отключение устройства.

Partial/failed/complete опрос без соседа не стирает его до прежнего expiry.
Это соответствует семантике текущего Agent. Failed poll сохраняется как
диагностика, но не добавляет новую link evidence.
Новое наблюдение той же связи обновляет время и expiry. Более старое сообщение
не подменяет новое. Измерения более чем на 30 секунд в будущем получают
`clock_skew` и доступны только в диагностическом режиме.
Запись с неправильным будущим временем не подменяет существующую корректную
связь. Когда время Agent исправлено, нормальное наблюдение заменяет ошибочное,
даже если его observed_at меньше старого неверного времени.
В collections предпочтён последний результат с допустимым временем;
при наличии только будущих результатов возвращается clock_skew:true.

## REST API и frontend

```http
GET /api/topology
GET /api/topology?agent_id=AGENT_ID
GET /api/topology?agent_id=AGENT_ID&device_id=DEVICE_ID
GET /api/devices/DEVICE_ID/topology?agent_id=AGENT_ID
GET /api/topology?include_expired=true
```

Ответ: generated_at, nodes, edges, collections, truncated, inventory_truncated.
Arrays всегда представлены массивами, в том числе при пустой карте.
`collections` содержит последний результат по каждой паре device/source:
frontend отличает «соседей нет» от «опрос завершился ошибкой».

Параметры:

| Параметр | Значение |
|---|---|
| agent_id | фильтр collector, до 256 байт |
| device_id | исходящее соседство конкретного устройства |
| include_expired | true/false; по умолчанию false |
| limit | observations в странице, 1–2000; по умолчанию 500 |
| offset | смещение observations, 0–1000000 |

Если device_id неоднозначен без agent_id, ответ 409. Неизвестный device_id —
404, неправильный параметр — 400, недоступная БД — 503.
Сам фильтр agent_id без существующих данных возвращает пустую карту.

Inventory ограничен 2000 записями, а коллекции — 2000 итогами. Ограничения
явно показываются флагами. При неполном inventory автоматическое resolution
отключается: неизвестный остаток мог содержать второй идентичный hostname.
`truncated:true` означает, что ответ не является полной картой; в том числе
это верно для страниц с offset>0. Для объединения страниц используются стабильные IDs.

Frontend может рисовать nodes/edges любым подходящим компонентом, показывать
source/protocol/порты в tooltip, выделять ambiguous/conflicting и обновлять
ответ API каждые 3 секунды. Это не меняет частоту сбора Agent.

`reported_online` — последнее сообщение устройства, `agent_connected` —
связь с collector. Неизвестным соседям online не назначается.
У минимальной записи, созданной только из topology, reported_online отсутствует
до появления inventory/telemetry: неизвестное состояние не выдаётся за offline.
Исправление бессрочного devices.online из пункта 8 в этот этап не входит.

## Надёжность и проверки

Проекции сохраняются в той же транзакции, что durable inbox. ACK возможен
после commit. Повторная доставка с тем же message ID не создаёт новый snapshot
или вторую связь. Ошибка откатывает запись целиком.
Observations отправляются PostgreSQL пакетами по 256, уменьшая число сетевых запросов.
Чтение inventory, observations и collections выполняется в одной read-only
транзакции Repeatable Read.

Проверки включают TTL boundary, позднюю доставку, clock skew, неоднозначность,
противоречие идентичности, бинарные порты, изоляцию Agent, replay, старые snapshots,
partial/failed/empty polls, раннюю topology и запись более одного пакета соседей.

Команды:

```sh
go fmt ./...
go vet ./...
go test ./...
```

Для проверок PostgreSQL задай TEST_DATABASE_URL отдельной тестовой базы.
Тесты используют собственные временные схемы.
Simulator из исходного Agent проверяет gRPC → PostgreSQL → REST;
пример `examples/topology.simulated.json` явно помечен source=simulated.
Результаты среды и ограничения проверки перечислены в validation.md.

Остальные пункты списка — logs/audit, telephony, commands, rollback management,
live ConfigUpdate, production PKI, online expiry, REST auth/roles и analysis —
остаются следующими этапами. В присланном Agent P3 сообщения ConfigUpdate
не обнаружено: этот этап потребует согласования протокола с его ответственным.
