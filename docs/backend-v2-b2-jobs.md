# B2.2 — очередь, планировщик и история операций источников

Дата: 11 октября 2026. Продолжение B2.1. Agent/Collector не изменялся;
на GitHub эта версия не публиковалась.

## Что добавлено

Миграция 019 добавляет `data_source_jobs`, `data_source_job_events` и поля
`next_sync_at`, `sync_cursor`, `sync_failures` к источнику. У каждого запуска
есть ID, версия настроек, происхождение manual/schedule, попытки, состояние,
время и фиксированный код результата. Внутренние credentials, cursor, lease
и session hash не возвращаются в REST.

Теперь доступны:

| Запрос | Назначение |
|---|---|
| `POST /api/data-sources/{id}/test` | Поставить реализованную проверку подключения в очередь |
| `POST /api/data-sources/{id}/sync` | Поставить реализованную read-only синхронизацию в очередь |
| `GET /api/data-sources/{id}/jobs` | История задач с limit/offset |
| `GET /api/data-sources/{id}/jobs/{job_id}` | Состояние конкретной задачи |
| `GET /api/data-sources/{id}/jobs/{job_id}/events` | История попыток и переходов |

POST требует действующую сессию администратора и один `Idempotency-Key`
из 1–128 печатных ASCII символов. Для новой операции используйте новый UUID.
Для повтора того же HTTP-запроса используйте прежний ключ. Ключ привязан
к источнику и операции: повтор возвращает ту же задачу с заголовком
`Idempotent-Replay: true`, даже если она уже завершилась.

Ответ 202 означает, что задача принята, а не что источник доступен или sync
завершён. Состояние нужно прочитать через GET. Чтение истории доступно всем
существующим ролям, запуск — только admin. Перед захватом ручной задачи
worker повторно проверяет действующую сессию и роль. Если администратора
отключили или он вышел, ещё не начатая задача получает `actor_revoked`.
Уже начатое чтение не отзывается задним числом.

## Жизненный цикл

`queued → running → succeeded`

При временной ошибке: `running → retry_wait → running`. Максимум три попытки.
После первой и второй ошибки ожидание составляет 2 и 4 секунды; worker
опрашивает очередь раз в секунду. Ошибки credentials/TLS, неизвестная ошибка
адаптера и некорректный ответ не повторяются автоматически. Timeout и
классифицированные временные сетевые ошибки могут повторяться.

`source_disabled`, `configuration_changed`, `actor_revoked` и снятый адаптер
приводят к `cancelled`. Неизвестные тексты ошибок и ответы внешнего сервера
не сохраняются: вместо них записывается безопасный код `adapter_error`.

## Защита от наложений и сбоев

- В базе установлен уникальный индекс: у источника может быть только одна
  активная queued/running/retry_wait задача, независимо от операции.
- Два worker обслуживают разные источники. Row locks и `SKIP LOCKED` позволяют
  захватить задачу только один раз. Ручной запрос при занятом источнике получает 409.
- Каждый запуск получает новый приватный lease token. Результат может записать
  только актуальная попытка с непросроченным lease. Повторное завершение отклоняется.
- Lease живёт `timeout_seconds + 15` секунд. После остановки backend активная
  задача сохраняется в БД. Следующий worker после истечения lease отмечает
  interrupted и может повторить чтение в пределах трёх попыток.
- Неверный или старый запуск не изменяет cursor. Cursor и успешный статус
  фиксируются в одной транзакции завершения задачи.
- При редактировании источника увеличивается revision. Результат со старой
  revision отменяется и не перезаписывает новые настройки. Настройка PUT
  консервативно сбрасывает cursor, чтобы не использовать позицию другого подключения.
- После трёх неуспешных попыток периодического sync планировщик отодвигает
  следующий запуск: минимум интервал источника или 30 секунд, затем увеличивает
  ожидание при последовательных неудачах до 24 часов. Успех сбрасывает счётчик.

Эта очередь предназначена для безопасного чтения. Реестр не принимает
операции без явного `ReadOnly=true`; пользователь не может передать произвольную
команду или код адаптера через API. Применение Ansible playbook и remediation
должны использовать отдельный контролируемый путь, а не автоматический retry.
Разработчик адаптера отвечает за соблюдение context timeout и реальную read-only
семантику. База не может сделать произвольную внешнюю операцию read-only.

## Что работает сейчас, а что ещё предстоит

В production зарегистрирован только **Collector test**: worker проверяет
существующую запись соединения и свежесть heartbeat. Проверка не подключается
к оборудованию заново и не меняет YAML. Успех test не выставляет
`last_successful_sync`: heartbeat не является sync оборудования.

У Collector capabilities `stream_status` и `test`; `sync` возвращает 409
`operation_unsupported`. Collector передаёт данные непрерывно по прежнему gRPC.
Для Zabbix, Prometheus, Ansible пока нет production адаптеров, их capabilities
пусты. test/sync для них возвращают явный 409; планировщик их не запускает.

Сам планировщик уже реализован и проверен на зарегистрированном тестовом
read-only адаптере: автоматически находит включённые источники с реализованным
sync, создаёт задачи по интервалу 3 секунды — 24 часа и не создаёт дубликаты.
Тестовый адаптер находится только в тестах, не подменяет реальную интеграцию.

Cursor хранится как внутренний JSON object до 16 KiB. Завершение job и cursor
атомарно; проекции будущих Asset/Observation ещё не реализованы и должны
интегрироваться в эту же транзакцию, а не сохраняться отдельно до завершения.

Ограничения этой версии:

- Ещё предстоит политика допустимых адресов/DNS/redirect/TLS/частных CA для
  внешних клиентов, затем реальные адаптеры B4/B5/B10. Сейчас внешних HTTP
  запросов нет; одна валидация HTTPS endpoint не заменяет сетевую защиту.
- История не очищается автоматически; политика хранения/архивации ещё нужна.
- Lease защищает jobs, но весь backend ещё не готов к нескольким replicas:
  старый startup по-прежнему сбрасывает Collector connected/session state.
- Постоянная потеря БД или нарушение context контракта самим адаптером требует
  восстановления среды; lease не гарантирует exactly-once внешнего чтения.
- `enabled=false` источника не отключает существующий gRPC Agent.

## Проверки

Проверяются реальные PostgreSQL transactions: idempotency, конкурирующие
schedulers, отсутствие двойного claim, retry, сохранение cursor только после
успеха, просроченный/старый lease, отмена после изменения/отключения источника,
отозванная сессия, лимит попыток и backoff, upgrade заполненной B2.1 базы.
Worker реально выполняет Collector test и корректно завершается при остановке.
HTTP тесты проверяют роли, обязательный ключ, 202/replay, 409 unsupported,
отсутствие приватного lease и сохранение прежних маршрутов.

Локальные результаты: `go fmt ./...`, `go vet ./...`, `go build ./...`,
`go test -count=1 ./...` прошли с PostgreSQL и неизменёнными Agent/Collector
executables: integration 110.702s, storage 148.907s. Дополнительные тесты
upgrade/трёх истечений lease/timeout/отключения источника прошли отдельно
после полного запуска (3.979s). Docker, race detector и реальное оборудование
в этой среде по-прежнему не проверены. GitHub публикации не было.
