# Этап 2: доступность устройств

Этапы 1 (карта topology) и 2 (availability) подготовлены только в текущей
локальной копии Backend. Они пока не опубликованы на GitHub. Исходники Agent
и protobuf-контракт не изменялись; Backend использует уже существующие сообщения
Agent P3. Этап 2 добавляет понятную оценку доступности, её причины и историю
сообщённых переходов.

## Четыре состояния

Backend различает состояние устройства и связь с его Agent. Например, последнее
сообщение о роутере может быть положительным, но уже слишком старым, чтобы
показывать роутер как доступный.

| Состояние | Что известно |
|---|---|
| `online` | Есть актуальное положительное наблюдение, связь с Agent актуальна |
| `offline` | Есть актуальное явное отрицательное сообщение, связь с Agent актуальна |
| `stale` | Последнее сообщение есть, но его срок истёк или связь с Agent потеряна |
| `unknown` | Достоверного сообщения о состоянии ещё нет |

Отсутствие метрик, пустой inventory, ошибки collector и исчезновение связи
не означают, что наблюдаемые устройства отказали. Старое `offline` тоже становится
`stale`: Backend сохраняет сообщённое отрицательное значение, но перестаёт
выдавать его за актуальное.

В карточке `availability.status` содержит эти четыре состояния. Поле
совместимости `online` равно `true` только при `availability.status:online`.
`reported_online` и `availability.last_reported_online` сохраняют последнее
принятое значение `true`/`false`; `null` означает отсутствие достоверного отчёта.
Для отображения недоступности проверяйте полный статус.

## Какие сообщения меняют состояние

| Сообщение | Наблюдение доступности |
|---|---|
| Telemetry | Положительное, по времени `sample.observed_at` |
| Inventory с `online:true` | Положительное; более старый `last_seen` сохраняет фактический возраст наблюдения |
| Inventory с `online:false` и `last_seen` | Явное отрицательное, по времени опроса inventory |
| Inventory с `online:false` без `last_seen` | Не создаёт отчёт: false может быть значением protobuf по умолчанию |
| `device.online` / `device.offline`, `source:remote` или `source:simulated` | Явное состояние устройства, по времени события |
| Hello | Сообщённое состояние локального устройства |
| Heartbeat | Положительное только для локального устройства своего Agent, по времени получения сервером |

Heartbeat не обновляет доступность всех удалённых устройств и не делает старую
telemetry свежей. Topology, события collector, logs и error reports сохраняются
в общем архиве, но сами по себе не подтверждают здоровье устройства.

Для положительного inventory используется более раннее из времени опроса
и `last_seen`, если `last_seen` указан. Для отрицательного inventory `last_seen`
подтверждает наличие осмысленной записи, а временем отрицательного наблюдения
служит время текущего опроса. Так старое положительное наблюдение не обновляется
просто потому, что его повторно прислали в новом пакете.

Выбор текущего отчёта учитывает время наблюдения, затем приоритет сообщения.
При одинаковом времени отрицательные события и inventory имеют приоритет
над положительными сообщениями. Положительная telemetry имеет приоритет над
положительным событием, чтобы сохранить её более короткий срок актуальности.
Для локального устройства heartbeat имеет наивысший приоритет при равном времени.
Более старые сообщения остаются в архиве, не перезаписывая выбранное состояние.

## Сколько действует наблюдение

Срок задаётся видом выбранного сообщения и monitoring policy устройства.
Для обычных наблюдений используется формула:

```text
stale_after_seconds = 2 × interval + min(30, max(5, interval / 10))
```

Деление на 10 целочисленное. Допуск учитывает задержки опроса и доставки.

| Источник | Интервал для расчёта |
|---|---|
| Telemetry | `telemetry_interval_seconds` |
| Inventory | `inventory_interval_seconds` |
| Событие устройства или перенесённая legacy-запись | Более длинный из telemetry/inventory |
| Hello / heartbeat | Точный `AGENT_TIMEOUT`, округлённый вверх до целых секунд |

Для hello/heartbeat `expected_interval_seconds:0`: период отправки не выводится
из тайм-аута связи. При defaults telemetry каждые 3 секунды действует 11 секунд;
inventory каждые 300 секунд действует 630 секунд. Интервал 86400 секунд даёт
172830 секунд актуальности. Для hello/heartbeat при `AGENT_TIMEOUT:90s`
срок составляет ровно 90 секунд.

`expires_at = observed_at + stale_after_seconds`. При достижении этого момента,
включая точную границу, отчёт становится `stale`. Запоздалая доставка не меняет
время наблюдения. Изменение policy пересчитывает срок исходного наблюдения;
Backend не утверждает, что новые интервалы уже применены в Agent. Его YAML
настраивается вручную.

## Ошибка часов и происхождение данных

Даты в ответах REST — UTC RFC3339. `observed_at` обозначает время наблюдения,
`received_at` — время приёма сервером; `time_basis` показывает `agent_observed`
или `server_receipt`. Heartbeat использует серверное время даже при неправильных
часах Agent. Поля `evidence_kind`, `source`, `message_id`, `event_id` помогают
проследить, откуда взялось состояние, и сохраняются при устаревании.

Наблюдение более чем на 30 секунд впереди времени приёма не заменяет последнее
достоверное состояние. Оно хранится отдельно как ошибка часов. Если достоверных
сообщений ещё нет, результат — `unknown`, `reason:clock_skew`,
`last_reported_online:null`. Если прежний отчёт есть, Backend сохраняет его
и выставляет `clock_skew:true`; сам статус может остаться `online`, `offline`
или `stale`. Более позднее принятое достоверное наблюдение снимает этот флаг.
Новое ошибочное сообщение снова выставляет флаг, даже если его дата ближе
к текущему времени, чем дата предыдущей ошибки.

При обычном отсутствии данных причина — `no_observation`; при потере связи —
`agent_disconnected`; при истечении срока — `observation_expired`. Актуальные
сообщения используют `device_reported_online`, `device_reported_offline`
или `agent_heartbeat`. Отсутствующие значения возвращаются явно как `null`,
пустые поля происхождения сообщения могут отсутствовать.

Симулятор может присылать данные по фиксированной временной шкале: это время
сценария, а не текущее время сервера. Сохраняется настоящий возраст наблюдения.
Данные с `source:simulated` следует явно обозначать в интерфейсе.

## Хранение, миграция и история

Миграция `005_availability.sql` добавляет:

- `availability_sources`: по одной текущей записи на устройство, вид сообщения
  и признак ошибки часов; число таких записей ограничено количеством видов;
- `device_availability_current`: одно выбранное достоверное состояние устройства;
- `device_availability_changes`: историю принятых изменений сообщённого значения;
- `availability_event_ids`: идентификаторы событий для защиты от повторов.

Исходные envelopes продолжают сохраняться в `agent_messages`. Inbox, проекция
и история записываются в одной транзакции; application ACK возвращается после
COMMIT. Известное устройство сохраняет последнее сообщение после перезапуска,
но потерянная связь с Agent делает его `stale` до восстановления соединения.

Миграция переносит квалифицированные старые состояния как `kind:legacy`:
для положительного состояния берётся `last_seen`, для отрицательного — время
сообщённого состояния. Пустой protobuf false и созданные только topology
заготовки не превращаются в отрицательные наблюдения. Это перенос известного
последнего состояния, а не восстановление полной истории из архива.
У legacy-записей ID исходного сообщения может отсутствовать.

История сжата: первое принятое сообщение имеет `from_online:null`, затем
добавляются только изменения `true → false` и `false → true`. Повтор того же
значения, истечение срока и отключение Agent не создают новых строк. Поэтому
эта история показывает сообщённые переходы и не является журналом всех отказов.

Точный повтор события с тем же ID не обновляет возраст или время приёма текущего
отчёта. Повторное использование ID с другим содержимым отклоняет весь пакет.
Реальные события `remote` дедуплицируются в пределах Agent между сессиями;
детерминированные ID Simulator учитываются в пределах его сессии, чтобы
отдельный запуск сценария мог повторить их.

## REST API и карта

| Запрос | Ответ |
|---|---|
| `GET /api/availability/summary` | Общая сводка; `?agent_id=...` ограничивает её одним Agent |
| `GET /api/devices/{id}/availability?agent_id=...` | Текущее состояние, причина, даты и источник |
| `GET /api/devices/{id}/availability/history?agent_id=...&limit=100&offset=0` | История, новые `id` первыми |

Для истории `limit:1..1000`, default 100; `offset:0..1000000`, default 0.
История существующего устройства без сообщений возвращает `items:[]`.
Несуществующее устройство даёт 404; одинаковый ID у нескольких Agent без
уточнения `agent_id` — 409. ID в URL нужно кодировать; для этих маршрутов
ID устройства и Agent ограничены 256 байтами UTF-8.

Список устройств, карточка, сводка и известные узлы topology используют одну
оценку доступности. У несопоставленного соседа на карте поле `availability`
может отсутствовать. Срок жизни связи topology остаётся отдельным свойством
наблюдения соседа и не подтверждает доступность самого устройства.

В сводке `total = online + offline + stale + unknown`. Дополнительные счётчики
`clock_skew` и `agent_disconnected` показывают проблемы, пересекающиеся
с этими четырьмя состояниями. Примеры полей — в [REST-контракте](api.md).
OpenAPI остаётся версии 3.0.3; версия API-описания — 0.4.0.

## Что проверено локально

- Проверки модели: отсутствие данных, явный offline, точная граница срока,
  интервалы 3 секунды и 24 часа, тайм-аут heartbeat, приоритеты и ошибка часов.
- 17 PostgreSQL integration tests: проекции, порядок сообщений, повторные
  события, конфликт ID с откатом пакета, сжатая история, миграция legacy,
  корректировка часов и согласованность сводки с карточками.
- Запуск Backend и неизменённого P3 Simulator со сценарием `device-recovery`:
  переходы `online → offline → online`, три записи истории; после отключения
  Agent сводка показала пять `stale`. Проверка выполнялась в отдельной схеме БД.

Сохранённые ответы Simulator: [offline](examples/availability.offline.simulated.json),
[восстановление](examples/availability.recovered.simulated.json),
[история](examples/availability.history.simulated.json),
[сводка после отключения](examples/availability.summary.simulated.json)
и [временная шкала](examples/availability.timeline.simulated.json).

Исходники Agent и протокол остались прежними. Native Linux e2e и запуск с race
detector в этом этапе не выполнялись. Проверка через Simulator подтверждает
обработку его сообщений; реальное оборудование SNMP/RouterOS в этом этапе
не проверялось. Очистка архивов/истории, incident engine и автоматическая
доставка новых policies в Agent пока не реализованы.
