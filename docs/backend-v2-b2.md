# B2.1 — реестр источников и защищённые учётные данные

Дата: 11 октября 2026. Это первая часть B2, а не завершённые интеграции B2–B10.
Код Collector/Agent не изменялся. Существующие endpoints и protobuf-контракт сохранены.
Этот документ описывает B2.1. Очередь и scheduler, отмеченные здесь как будущие,
добавлены следующим этапом: [B2.2](backend-v2-b2-jobs.md), OpenAPI 0.19.0.

## Что работает

- Независимые экземпляры COLLECTOR, ZABBIX, PROMETHEUS, ANSIBLE. Например,
  Zabbix PROD и TEST имеют разные `src_...` ID, даже при одинаковом endpoint.
- Миграция 018 создаёт `data_sources` и `data_source_audit`. Старые таблицы не
  заменяются. Источники и история сохраняются после повторного запуска миграций.
- Источник Collector связывается с существующим `agent_id` через `connection_ref`.
  Одна ссылка не может зарегистрироваться дважды. Регистрация источника не
  обязательна для работы старого gRPC: существующие агенты продолжают подключаться.
- `GET /api/data-sources?limit=50&offset=0` возвращает список с пагинацией.
- `POST /api/data-sources` создаёт подключение.
- `GET /api/data-sources/{id}` и `GET /api/data-sources/{id}/status` возвращают
  настройки и актуальный статус.
- `PUT /api/data-sources/{id}` заменяет настройки с проверкой `revision`.
  Запрос со старой ревизией получает 409 и ничего не перезаписывает.
- Чтение доступно viewer/operator/admin; изменения — только admin. Действительность
  сессии перепроверяется в транзакции с тем же блокированием, что и изменения пользователей.
- Изменение и аудит записываются в одной транзакции. В журнал попадают ID,
  автор, действие и ревизия; пароль/токен не попадают.

## Учётные данные

`credential` — поле только для записи. Ответ содержит только `has_credential`.
В PostgreSQL хранится AES-256-GCM ciphertext с независимым случайным nonce.
ID источника участвует в аутентификации ciphertext: перенос зашифрованного
пароля в другое подключение обнаруживается.

`DATA_SOURCE_ENCRYPTION_KEY` — base64 от 32 случайных байтов, задаётся окружением.
В `.env.example` оставлено пустое значение, Docker Compose передаёт переменную.
Без ключа можно регистрировать источники без credentials; попытка сохранить
непустой credential получает 503. Пример создания ключа в PowerShell:

```powershell
$sourceKeyBytes = [byte[]]::new(32)
[System.Security.Cryptography.RandomNumberGenerator]::Fill($sourceKeyBytes)
[Convert]::ToBase64String($sourceKeyBytes)
```

Сохраните результат локально в окружении запуска и отдельно в резервной копии.
Реальный ключ нельзя выкладывать в репозиторий. При утрате ключа credentials
нельзя восстановить из одной базы данных. Процедура ротации ещё не реализована.
Если в БД уже есть ciphertext, запуск с отсутствующим или другим ключом
останавливается с понятной ошибкой без замены сохранённых данных.

- Отсутствующий / `null` credential при PUT сохраняет прежнее значение.
- Пустая строка удаляет credential.
- Непустая строка заменяет его новым зашифрованным значением.
- Изменение endpoint требует явной замены или удаления существующего credential:
  старый токен не переносится молча на другой сервер.
- В endpoint запрещены HTTP, userinfo, query и fragment. Не размещайте секреты
  в пути URL или имени источника: для них предназначено только поле credential.

## Примеры для фронтенда

Создание Zabbix без токена (его можно установить отдельным PUT):

```json
{
  "type": "ZABBIX",
  "name": "Zabbix PROD",
  "endpoint": "https://zabbix.example/api_jsonrpc.php",
  "enabled": true,
  "sync_interval_seconds": 30,
  "configuration": { "timeout_seconds": 15 }
}
```

Создание связи с уже зарегистрированным Collector:

```json
{
  "type": "COLLECTOR",
  "name": "Collector основной сети",
  "connection_ref": "agent-1",
  "enabled": true,
  "sync_interval_seconds": 3,
  "configuration": { "timeout_seconds": 15 }
}
```

PUT передаёт полный набор настроек и текущую `revision`. Тип существующего
источника не меняется: другой тип создаётся отдельным экземпляром.
Точный контракт опубликован в `/openapi.json`, версия 0.18.0.

## Честные статусы и ограничения

Collector `connected` означает свежий heartbeat существующего gRPC stream.
Истёкший heartbeat или разрыв соединения дают `disconnected`. Это не утверждение,
что каждое удалённое устройство включено или выключено. `last_successful_sync`
для потокового Collector остаётся null: heartbeat не является завершённой sync.

Внешние источники показывают `adapter_unavailable`, а список capabilities пуст.
У Collector доступна только `stream_status`. Здесь ещё нет сетевых запросов к
Zabbix/Prometheus/Ansible и никто не проверяет доступность введённого endpoint.
Регистрация подключения сама по себе не означает успешную интеграцию.

`enabled=false` отключает запись источника для будущих операций интеграции.
Это не команда остановки Agent и не изменение существующего gRPC admission.
`sync_interval_seconds` хранится в диапазоне 3 секунд — 24 часа, но пока не
запускает scheduler и не изменяет YAML Collector. Динамический Collector config — B9.

## Что осталось в B2

1. Реестр реально реализованных операций адаптеров, без обязательного общего
   интерфейса для Collector stream, Prometheus queries и Ansible jobs.
2. Асинхронные test/sync, таблицы jobs/history/cursor, идемпотентная ручная очередь.
3. Scheduler с lease, timeout/backoff, восстановлением после рестарта и защитой
   от пересечения ручной/периодической синхронизации.
4. Ограничение разрешённых адресов, DNS/redirect policy, проверка TLS и частных CA
   до появления любого внешнего HTTP-клиента. Одной проверки URL недостаточно.
5. История операций и аудит через API. B3 добавит Asset/SourceBinding; B4 — настоящий
   Zabbix adapter. Регистрация данных источника уже имеет независимый ID для этого.

## Проверки

Добавлены тесты: AES-GCM/tamper/source isolation, валидация URL/интервалов,
HTTP роли и отсутствие секрета в ответе; PostgreSQL — независимость экземпляров,
шифрование, сохранение/удаление credentials, optimistic concurrency, отказ с
неверным ключом, запрет записи после logout, аудит, Collector expiry и миграция.
Тестовая PostgreSQL работает в отдельных удаляемых schemas на loopback:55432.
Данные пользовательской базы не очищаются. Docker/race/реальное оборудование
требуют отдельной проверки в подходящей среде, как и на B0/B1.

Результаты этой локальной проверки: `go fmt ./...`, `go vet ./...`,
`go test -count=1 ./...` прошли. Полный запуск включал PostgreSQL и реальные
исполняемые файлы прежнего Agent и нового Collector d456fea:
integration 124.480s, storage 165.946s. После уточнения ID `src_...` и добавления
проверки истечения heartbeat повторно прошли тесты DataSource на PostgreSQL,
config, API и доменные тесты; vet прошёл повторно.
