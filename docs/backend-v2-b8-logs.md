# B8.2 — логи и audit в карточке Asset

Этот этап связывает уже принимаемые логи с единой инвентаризацией. Collector и его protobuf-контракт не меняются. Backend продолжает сохранять сообщения в `agent_messages`, нормализованные записи — в `log_records`, audit-поля — в `audit_records`. Новая таблица копий логов не нужна: добавлены запросы по текущим привязкам оборудования и два индекса в миграции `029_asset_logs.sql`.

## 1. Как запись попадает в карточку оборудования

1. Backend принимает `LogBatch` от зарегистрированного Collector.
2. Существующая обработка проверяет границы сообщения и дополнительные `SyslogMetadata` / `ObservationMetadata`, нормализует время, дополнительно маскирует известные секреты и сохраняет запись в транзакции. Подтверждение отправляется после успешного сохранения.
3. Для карточки Asset Backend находит источник типа `COLLECTOR`, у которого `connection_ref` точно равен `agent_id` отправителя.
4. Требуется уже существующая привязка инвентаризации: тот же `source_instance_id`, `external_type=device`, тот же `device_id` и тот же `record_scope`. Дополнительно проверяются `legacy_agent_id` и `legacy_device_id` владельца.
5. Только такая привязка определяет текущий `asset_id`. Лог сам по себе не создаёт Asset и не объединяет оборудование.

Два Collector могут прислать `device_id=system`, одинаковый hostname и одинаковый IP. Их записи останутся раздельными, пока проверенная операция объединения Asset не соединит соответствующие привязки. Имена и адреса не используются для автоматической привязки отправителя лога.

В ответе есть `association=source_owned_device_reference`: это ссылка устройства в отчёте Collector, а не независимое доказательство физической личности отправителя syslog. Поля `SourceRef.target_id`, `instance_id` и `resource_id` сохраняются как логическое происхождение наблюдения; они не заменяют проверку привязки.

## 2. Заявленный hostname и транспорт — разные данные

В `host` остаётся имя из заголовка сообщения. В `syslog` отдельно сохраняются сообщённые Collector:

- `peer_ip` — адрес сетевого соседа;
- `transport` — UDP, TCP или TLS;
- `tls_identity` и `authenticated` — сведения о проверке TLS-отправителя;
- `managed`, `format`, `parse_status`, structured data и другие поддерживаемые поля.

Backend проверяет допустимость сочетания этих полей, но не устанавливает заново TLS-соединение с syslog-отправителем. Вся транспортная информация здесь — отчёт Collector. Заявленный hostname может отличаться от TLS identity и peer IP; отличие сохраняется и не приводит к подмене Asset.

Неизвестный `device_id`, который ещё не присутствовал в инвентаризации, сохраняется в общем журнале и доступен через существующие API логов. Он не исчезает и не приклеивается к похожему hostname. Когда для этого точного источника и устройства появляется инвентаризационная привязка, накопленные записи становятся доступны в соответствующей карточке Asset.

## 3. Реальное оборудование и симуляция

Для source=simulated и typed ObservationMetadata.Source.provenance=simulated (на записи или batch) новые логи получают scope исходной сессии. Обычные записи имеют пустой scope. Asset API сравнивает этот scope с binding inventory; пустой record_scope filter выбирает реальные записи, отсутствие фильтра — все привязки выбранного Asset.

Старые typed simulation записи могли сохраниться с пустым record_scope. Новый read query использует их immutable inbox session и сохранённую provenance, не приклеивая их к реальному устройству. Строки, fingerprints и audit keys сохраняются как были; reread этой же старой записи не создаёт вторую строку. Старый audit key может отражать прежний пустой scope, поэтому группировка дополнительно отделяет effective session в Asset API и не объявляет это доказательством полноты.

## 4. Объединение и разделение Asset

В таблице логов нет выдуманного «исторического Asset ID». Запрос использует текущую привязку источника:

- после объединения карточка назначения показывает записи от обеих привязок;
- у merged alias нет прежних привязок, поэтому его список пустой; его карточка Asset по-прежнему содержит `merged_into_id`;
- после разделения старые записи соответствующего источника переходят в новую карточку вместе с привязкой;
- исходные записи, времена, `record_id`, `message_id` и audit-ключи не переписываются.

Ответ всегда содержит текущие `asset_id`, `binding_id`, `source_instance_id`, `agent_id`, `device_id` и `record_scope`, чтобы frontend мог объяснить источник данных.

## 5. Поиск и пагинация

Добавлены маршруты:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/assets/{id}/logs` | Поиск нормализованных записей выбранного Asset |
| `GET /api/assets/{id}/logs/{log_id}` | Одна запись с проверкой принадлежности Asset |
| `GET /api/assets/{id}/audit/events` | Сгруппированные audit-события |
| `GET /api/assets/{id}/logs/{log_id}/raw` | Контролируемый доступ администратора к сохранённому, уже замаскированному raw-тексту |
| `GET /api/logs/{log_id}/raw` | Такой же контролируемый raw-доступ для общей записи, включая ещё не привязанных отправителей |

Обычное чтение требует `data.read`. Raw-маршруты требуют администратора; подробности ниже.

Новые запросы используют существующие фильтры logbook: `q` для полнотекстового поиска, `contains` для подстроки, `source`, `source_id`, `host`, `process`, `severity`, `facility`, времена `from` / `to`, audit-поля и другие разрешённые фильтры. Дополнительно можно ограничить `source_instance_id` и точный `record_scope`. `q` и `contains` одновременно не допускаются. Текстовые фильтры ограничены 256 байтами, `limit` — 1…200, курсор `before_id` — положительное числовое ID. HTTP-обработчик отклоняет неизвестные или повторяющиеся параметры; параметра `include_raw` нет.

Пример:

```text
GET /api/assets/asset_.../logs?q=denied&limit=50
GET /api/assets/asset_.../logs?source_instance_id=src_collector_...&limit=50
GET /api/assets/asset_.../logs?record_scope=&limit=50
GET /api/assets/asset_.../audit/events?record_type=SYSCALL&limit=20
```

Записи идут по убыванию числового ID; `next_before_id` переносится в следующий запрос. Это пагинация по сохранённой последовательности, а не обещание сортировки по времени события: задержанная доставка и original timestamp сохраняются отдельно. `original_timestamp`, `observed_at`, `received_at` и `time_basis` показывают, какое время использовано; неизвестное исходное время не заменяется выдуманным.

Полнотекстовый поиск и обычные ответы работают с нормализованной, дополнительно замаскированной проекцией. Маскирование известных шаблонов не является гарантией удаления любых возможных персональных данных: правила отправляемых данных и секретов нужно также настроить у Collector.

## 6. Audit-события не обрезаются фильтром отдельных строк

Audit event key уже учитывает Collector, device ID, scope, source, файл, host и event ID. Повторная доставка не создаёт новое событие.

При фильтре `record_type=SYSCALL` или `q` Backend сначала выбирает совпавшие события, затем собирает **все записи каждого выбранного события**. Если в событии есть SYSCALL и PATH, `record_count=2` и оба типа сохраняются. Это предотвращает ложные выводы о числе записей и outcome.

Поля `outcome` имеют значения `success`, `failure`, `mixed` или `unknown`. `completeness=unknown`: Backend не считает наличие двух строк доказательством полноты audit-события. Курсор группы — максимальный ID строки события; группы не повторяются на границе страниц.

Получить строки группы можно через список логов выбранного Asset с `event_key=audit:<64 hex>` и audit-фильтром. Право на выбранный Asset проверяется тем же запросом; знание чужого event key не даёт доступ к чужой карточке.

## 7. Raw: отдельный доступ, живая сессия и запись в audit

Обычный новый ответ Asset не содержит raw-текст вообще. Обычные legacy-ответы сохраняют прежнюю структуру `logbook.Record`, но поле `raw` возвращается пустым: это закрывает обход ограничений через общий журнал. Из opaque `syslog` / `observation` также удаляются любые raw payload-поля, в том числе из вложенных JSON.

Raw-маршрут возвращает одну запись размером не более 256 KiB. Он читает **уже нормализованный и замаскированный `log_records.raw`**. Original inbox, raw binary syslog payload и другие сообщения не возвращаются. Redaction не отменяется даже для администратора. `archive_payload_not_exposed=true` сообщает об этой границе; `raw_payload_available` отражает, что исходная запись сообщала дополнительный binary payload, который не опубликован этим маршрутом.

Кроме HTTP-проверки права, Store повторно проверяет в PostgreSQL действующую сессию, реальную роль admin, срок сессии и отсутствие блокировки пользователя. Изменения роли синхронизированы общим advisory lock; строка пользователя и сессии блокируются для чтения до конца операции, поэтому отзыв сессии не проскальзывает между проверкой и выдачей.

Успешное чтение записывается в `access_audit` с действиями `asset_log_raw_read` либо `log_raw_read`, ссылкой на запись, request ID и peer. Если запись audit не сохранилась, привилегированный raw-текст не возвращается. Даже во внутреннем вызове без HTTP identity raw-доступ запрещён.

Неизвестный Asset и чужой log ID дают 404. Отсутствующее право или отозванная сессия дают запрет доступа. Клиент не может передать свой URL, другой source ref или raw-флаг для обхода проверок.

## 8. Что проверено

Тесты проверяют PostgreSQL и реальные обработчики хранения:

- одинаковый device ID у двух Collector остаётся раздельным;
- Host, SourceRef target и транспортные сведения не используются для угадывания Asset;
- неизвестный отправитель сохраняется в общем журнале;
- повторы и reread не дублируют строки;
- симуляция отделена от реального оборудования и другого запуска;
- merge и split корректно меняют текущую принадлежность старых логов;
- audit-фильтр выбирает целое событие, курсор не повторяет группы;
- raw недоступен viewer/operator, чужому Asset, истёкшей или отозванной сессии;
- заявленная роль admin без соответствующей реальной роли в БД не принимается;
- ошибка записи audit не возвращает raw;
- обычные JSON-ответы не содержат raw-текст и binary payload;
- generic raw для неизвестного отправителя не создаёт привязку и сохраняет маскирование.

Проверка на настоящем syslog-сервере и оборудовании остаётся частью итоговой интеграции команды. Здесь не добавляется новый syslog listener в Backend: сбор и транспорт уже выполняет неизменённый Collector.

## Подключение в Backend

В `Store.Migrate` зарегистрирована миграция `029_asset_logs.sql`; новых ingestion hooks нет. HTTP подключает методы `AssetLogs`, `AssetLog`, `AssetAuditEvents`, `AssetLogRaw`, `LogRaw`, типы из `internal/assetlogs` и masking helper `assetlogs.SafeLegacy`. Общие API-обработчики подключены; OpenAPI 0.29.0 описывает итоговые маршруты B8.
