# B8 — аппаратные данные, логи и телефония в карточке Asset

## Что получено

Раньше аппаратная информация, логи и SIP уже принимались от Collector, но их приходилось искать в отдельных представлениях устройств. Теперь Backend даёт API для чтения этих данных через общую карточку оборудования — Asset. Frontend другой разработчик сможет собрать из этих маршрутов вкладки «Аппаратная часть», «Логи», «Телефония».

Изменён только Backend. Код Collector/Agent, его protobuf-контракт и frontend не редактировались. Публикации, commit и push в этом этапе нет.

## 1. Откуда берутся данные

Collector подключается по существующему двустороннему gRPC stream. Backend сохраняет исходное сообщение и нормализованные данные в одной транзакции PostgreSQL. Только после commit отправляется ACK. Если соединение пропало до ACK, повторное сообщение не создаёт вторую запись.

Для оборудования используется Asset Registry B3. Источник и его точный ID устройства определяют SourceBinding, а текущая привязка определяет Asset. Название или IP сами по себе не объединяют оборудование. При merge/split исторические данные следуют за привязкой, исходные сообщения не переписываются.

## 2. Аппаратная часть

Новый слой хранит отдельно текущие значения и историю hardware. Поддерживаются System, Chassis, Manager, компоненты, питание, firmware, аппаратные health/status и переданные сенсоры. Сохраняются SourceRef, resource ID, происхождение, времена наблюдения/сбора/источника и качество времени.

Значение датчика 0 остаётся нулём; неизвестное значение не становится нулём. PowerState=Off не превращается в Critical: питание и аппаратное здоровье — отдельные признаки.

Карточка System может дополнительно получить данные связанного BMC по доказанной management relation B7. Ответ сохраняет настоящий Asset-владелец каждого значения и relation IDs. При неоднозначной или слишком большой карте Backend не угадывает связь. Подробнее: [аппаратные данные](backend-v2-b8-hardware.md).

## 3. Логи и Linux audit

Новые запросы используют существующие log_records/audit_records, а не вторую копию логов. Добавлены индексы, поиск по Asset, source/session filters и группировка audit-событий.

Заявленный hostname сообщения и транспортные peer IP/TLS identity сохраняются отдельно. Непривязанный syslog sender остаётся в общем журнале. Backend не выбирает ему Asset по похожему имени.

Обычные ответы скрывают raw. Для администратора есть отдельный маршрут к уже замаскированному сохранённому тексту. Store ещё раз проверяет действующую сессию в БД и сохраняет audit чтения перед выдачей. Это действует и для общего журнала: старое поле raw теперь пустое в обычных ответах. Подробнее: [логи и audit](backend-v2-b8-logs.md).

## 4. SIP/VoIP

Администратор явно подтверждает, как наблюдённая SIP-точка относится к физическому Asset. Перед записью Backend проверяет существующий binding, источник Collector, наблюдённые address/transport/source, scope и актуальные revisions. Изменение имеет причину, idempotency key и историю.

Так можно привязать реальную АТС, известную только Zabbix, к SIP-проверкам Collector. Источник inventory и источник SIP сохраняются отдельно. Для симуляции разрешён только её Collector и точная сессия.

Карточка возвращает latest/history, доступность, latency/response code, физическое размещение, Asset ID узла карты и существующие SIP-инциденты соответствующей точки. Смена адреса или транспорта требует повторной проверки связи. Подробнее: [телефония](backend-v2-b8-voip.md).

## 5. Основные маршруты для frontend

| Запрос | Что показывает |
| --- | --- |
| GET /api/assets/{id}/resolved-inventory | Сводная inventory B6 |
| GET /api/assets/{id}/placement | Проверенное физическое размещение B6 |
| GET /api/assets/{id}/hardware | Текущие hardware-наблюдения |
| GET /api/assets/{id}/hardware/history | Историю hardware |
| GET /api/assets/{id}/logs | Поиск по нормализованным логам |
| GET /api/assets/{id}/logs/{log_id} | Одну принадлежащую Asset запись |
| GET /api/assets/{id}/audit/events | Сгруппированные audit-события |
| GET /api/assets/{id}/voip | Связанные SIP-сервисы и контекст |
| GET /api/assets/{id}/voip/{association_id}/history | Историю проверенной SIP-точки |
| GET /api/assets/{id}/voip/{association_id}/events | Историю решений о связи |
| POST /api/assets/{id}/voip | Подтверждённую привязку SIP, admin |
| PUT /api/assets/{id}/voip/{association_id} | Пересмотр связи SIP, admin |
| GET /api/assets/{id}/logs/{log_id}/raw | Замаскированный raw, admin + audit |
| GET /api/logs/{id}/raw | То же для общей записи, включая неизвестного sender |

Все чтения требуют входа и data.read; raw и изменение связей — access.manage/admin. Cookie-запросы на изменение используют существующую CSRF-защиту. Обновлён OpenAPI до 0.29.0, доступный через /openapi.json. Неизвестные/повторные параметры новых маршрутов отклоняются, ошибочное URL-кодирование не игнорируется.

## 6. Как проверить у команды

1. Распаковать архив и запустить Backend по README с существующим PostgreSQL или Docker Compose. Backend сам применит миграции 028–030. Для обновления работающей базы предварительно сделать обычную резервную копию.
2. Запустить неизменённый Collector с подготовленными Redfish/IPMI, syslog/file/audit и SIP targets. Убедиться, что source и inventory пришли через gRPC.
3. Войти в Backend через /api/auth/token, получить Asset IDs через /api/assets и проверить bindings.
4. Прочитать /hardware и /hardware/history. Проверить, что видны источник и времена, Power Off не показан как аппаратная авария.
5. Прочитать /logs?q=denied и /audit/events. Unknown sender искать через общий /api/logs, пока нет точной inventory-привязки.
6. Получить настоящие наблюдённые SIP-параметры через прежний telephony API, подтвердить связь с существующим binding, прочитать /voip и history.
7. Повторить чтения от viewer; raw должен вернуть 403. Повторить доставку сообщения и убедиться, что данных не стало вдвое больше.

Локальные fixtures проверяют обработку и совместимость; они не заменяют приёмку на физических датчиках, настоящем syslog/АТС и стендах команды. Zabbix/Prometheus стенды команда пока не предоставила.

## 7. Обновление базы и границы этапа

028 создаёт hardware samples/latest и переносит только текущую подтверждённую inventory плюс квалифицированное последнее hardware-сообщение для привязки. Полный исторический inbox не копируется при старте; старый raw архив сохраняется. 029 добавляет индексы логов. 030 создаёт reviewed VoIP associations, события, idempotency operations и SQL-проверки ownership.

Старые typed-simulation логи с пустым record_scope читаются по исходной сессии из сохранённого envelope. Их строки, fingerprint и audit keys не переписываются; reread этой же записи не создаёт копию. Новые typed simulation записи сразу получают scope сессии. SIP-история и health rules разделяют реальные и симулированные наблюдения.

После B8 следующая часть окончательного плана — B9: управление конфигурацией Collector без перезапуска. Затем B10–B16: Ansible, drift, общая корреляция, AI, отчёты, TSDB и итоговое усиление/интеграция. Managed Collector configuration пока не объявляется реализованной. B8 не добавляет новый сборщик, автоматическое устранение аварий или frontend.

Результаты прогонов и ограничения среды: [проверки B8](backend-v2-b8-validation.md).
