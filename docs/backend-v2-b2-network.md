# B2.3 — защищённый HTTP-клиент внешних источников

Дата: 11 октября 2026. Это инфраструктура будущих Zabbix/Prometheus/Ansible
адаптеров. Сами адаптеры пока не зарегистрированы; успешного подключения к
реальным внешним системам эта версия не заявляет. Agent/Collector не менялся.

## Что добавлено

`datasources.NetworkPolicy` хранит ограничения окружения запуска.
`datasources.NewSourceHTTP(policy, source)` создаёт отдельный HTTPS-клиент
для конкретного источника. Настройки загружаются в `Config.DataSourceNetwork`;
будущие адаптеры должны пользоваться этим клиентом, а не `http.DefaultClient`.

По умолчанию внешние адреса запрещены. Для подключения требуются одновременно:

1. Разрешённый HTTPS origin — имя сервера и конкретный порт.
2. Разрешённый IP или подсеть, в которую попадает каждый результат DNS.
3. Доверенный сертификат для имени сервера, включая обычную проверку срока.

В API источника можно указать только `tls_ca_ref` — имя заранее настроенного
CA. Нет `insecure_skip_verify`, пути к файлу, proxy или произвольных HTTP headers.
Попытка передать неизвестное поле конфигурации через REST получает 400.

## Настройка окружения

Пример для Zabbix в собственной сети:

```dotenv
DATA_SOURCE_ALLOWED_ORIGINS=https://zabbix.example:443,https://prometheus.example:9090
DATA_SOURCE_ALLOWED_CIDRS=10.20.0.15/32,10.20.0.16/32
DATA_SOURCE_ALLOW_LOOPBACK=false
DATA_SOURCE_CA_FILES={"lab":"/run/source-ca/lab.pem"}
```

Это примеры, их нужно заменить адресами своего стенда. Лучше разрешать
конкретные IP `/32` и `/128`, когда они постоянные. HTTPS origin не содержит
путь, query или credentials; путь API хранится отдельно в endpoint источника.
`https://zabbix.example` и `https://zabbix.example:443` обозначают один origin.
Порт `8443` — отдельный origin, который нужно разрешить явно.

`DATA_SOURCE_CA_FILES` — JSON-объект: имя CA → путь к файлу в окружении backend.
В Docker файл необходимо отдельно смонтировать read-only в контейнер; одной
переменной недостаточно. Базовый Compose передаёт переменные, но не предполагает
конкретное расположение пользовательских CA. Например, в своём override:

```yaml
services:
  backend:
    volumes:
      - ./source-ca/lab.pem:/run/source-ca/lab.pem:ro
```

Файл должен содержать только публичные CA certificates в PEM, не private key
и не обычный leaf certificate. Ограничение: 1 MiB на bundle, до 32 ссылок.
Некорректный файл или mapping останавливает запуск с понятной ошибкой.
Без `tls_ca_ref` используется системное доверие. При указанной ссылке
используется только выбранный CA bundle: он не добавляется глобально к
доверию всех других источников и не заменяет mTLS CA агента.

При создании/изменении источника конфигурация выглядит так:

```json
{
  "timeout_seconds": 15,
  "tls_ca_ref": "lab"
}
```

Пустая или отсутствующая ссылка означает системное доверие. Ссылка должна
состоять из ASCII букв, цифр, `_` и `-`, длина до 64 символов, первый символ
буква/цифра. Для Collector она должна быть пустой: его TLS настраивается
в прежнем gRPC/PKI механизме. Изменение settings проходит через прежний
PUT с revision check и аудитом.

Для изолированных HTTPS fixtures на своём компьютере можно отдельно разрешить
loopback, но только при числовом loopback HTTP listener backend. Всё равно
нужны origin и CIDR. В обычном Compose listener `0.0.0.0`, поэтому включать
этот флаг там нельзя; сервисы стенда нужно подключать по внутренней сети Docker.

## Как защищается запрос

- Только HTTPS, без userinfo, query и fragment в сохранённом endpoint.
  Недопустимые порты, control characters, обратные слеши и `..` пути отклоняются.
- URL нормализуется по имени и порту. Обновление старой записи без `:443`
  не переносит credential на другой сервер и не требует повторного токена.
- При новом TCP соединении клиент получает DNS results, проверяет **все**
  адреса и соединяется непосредственно с проверенным числовым IP. Повторного
  разрешения имени внутри dial нет. Если DNS содержит хотя бы один запрещённый
  адрес, весь ответ отклоняется. Максимум 16 адресов в ответе.
- TLS проверяет исходное имя сервера, а не только IP. Минимум TLS 1.2;
  `InsecureSkipVerify` не включается. Используется HTTP/1.1.
- Перенаправления 3xx не выполняются, даже внутри разрешённых origins.
  Authorization не переносится на другой сервер. Ответ имеет фиксированный
  код `redirect_blocked`; тело и Location не сохраняются в job.
- Переменные `HTTP_PROXY`/`HTTPS_PROXY` не влияют на этот transport. Нет cookie
  jar и пользовательского Host header. Adapter paths относительные и не могут
  указать другой origin; query формируется через `url.Values`.
- Body запроса ограничен 1 MiB, ответа — 4 MiB, response headers — 32 KiB.
  Размер проверяется и для Content-Length, и при потоковом чтении. Сжатые
  ответы не распаковываются: для них возвращается `invalid_response`.
- У запроса есть общий timeout источника 1–120 секунд и context worker.
  Есть отдельные connect/TLS/header таймауты. Ожидание body тоже ограничено.
- Тексты сетевых ошибок, URL и ответы с ошибкой не попадают в журнал задач:
  возвращаются фиксированные `network_policy_rejected`, `tls_failed`,
  `response_too_large`, `redirect_blocked`, `connection_failed`, `timeout`.
  Ошибки policy/TLS/redirect/размера не повторяются очередью автоматически.

Стандартный Go transport может повторить безопасный запрос после разрыва
ранее использованного соединения. Новый dial снова проходит DNS/IP policy;
общий timeout остаётся в силе. Прикладные повторы остаются под контролем
очереди B2.2 с пределом в три попытки.

## Адреса, которые нельзя разрешить обычным allowlist

Даже широкий CIDR не разрешает unspecified, link-local, multicast, IPv4
reserved `0/8`, `240/4`, известные metadata `169.254/16`, `100.100.100.200`,
`fd00:ec2::254`, а также NAT64/6to4/Teredo translation ranges. IPv4-mapped IPv6
проверяется после нормализации к IPv4. Loopback требует отдельного lab-флага.

Это защита transport, не универсальная замена firewall: политика маршрутизации,
нестандартные NAT/proxy, скомпрометированные разрешённые серверы и управление
самим окружением требуют отдельной защиты. Allowlist меняется через конфигурацию
развёртывания и рестарт backend, а не через REST пользователя.

## Совместимость и границы этапа

Новой SQL миграции нет: `tls_ca_ref` хранится в существующем JSON settings.
Старые записи с отсутствующим полем читаются с системным доверием. Старые REST
маршруты и protobuf остаются; OpenAPI теперь 0.20.0.

Регистрация endpoint ещё не выполняет сетевой запрос. Никаких запросов к
неизвестным реальным системам при запуске не добавлено. Существующий Collector
test работает по состоянию stream. Zabbix/Prometheus/Ansible по-прежнему
показывают отсутствие adapter capabilities, test/sync возвращают 409.

Базовая инфраструктура B2 теперь содержит реестр, credentials, очередь,
scheduler, cursor/history, аудит и защищённый transport. Реальная интеграция
и её end-to-end приёмка выполняются в B4/B5/B10. HA всего backend, ротация
ключа credentials, автоматическая очистка истории jobs и атомарные будущие
Asset projections остаются отдельными задачами, как отмечено в B2.1/B2.2.

## Проверки

Локальные TLS-серверы и управляемые DNS fixtures проверяют доверенный/недоверенный
CA, SAN hostname, DNS rebinding, mixed DNS answers, запрет redirects без
передачи токена второму серверу, игнорирование proxy env, ограничение обычного
и chunked body, отказ от compressed body, context deadline и relative paths.
Отдельно проверяются metadata/IPv6 policy, настройки deployment/CA file,
запрет private key в trust bundle и запрет REST TLS bypass. PostgreSQL проверяет
сохранение credential при нормализации старого endpoint.

Результаты локального запуска: `go fmt ./...`, `go vet ./...`, `go build ./...`
и `go test -count=1 ./...` прошли с PostgreSQL и неизменёнными Agent/Collector
executables. Integration: 110.440s, storage: 151.839s. После уточнения обработки
ошибки policy в конструкторе доменные/API тесты и vet проверены повторно.
Docker/race/настоящие внешние системы требуют отдельной приёмки; GitHub не изменён.
