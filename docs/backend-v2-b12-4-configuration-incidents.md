# B12.4 — инциденты отклонения конфигурации

B11 сравнивает фактическую конфигурацию с утверждённым администратором эталоном. B12.4 подключает результаты к общим incidents и correlation. Agent, Collector и frontend не изменены. Сбор выполняется существующим Ansible Worker; новый код не запускает команды и не предоставляет автоматического исправления.

## Как работает

Результат сравнения и запись в configuration_signal_pending сохраняются одной транзакцией. Worker обрабатывает до 25 Asset за проход. Для каждого берётся последний снимок текущего эталона по actual_observed_at, а не последний ручной запрос сравнения. Поэтому повторное сравнение старой compliant-конфигурации не закрывает более свежий drift. Пока automation отключён в backend, очередь сохраняется до включения.

Требуются реальный scope, наблюдаемое оборудование без конфликта сопоставления, неизменившаяся revision оборудования, действующий включённый automation target с той же revision/template, одинаковая поддерживаемая версия normalizer и свежий снимок. Предел свежести наследует B11: по умолчанию 15 минут. Future timestamp вне допустимых 30 секунд, unknown/unsupported и старый снимок не создают warning и не подтверждают recovery.

Подтверждённый drift с ненулевым количеством изменений создаёт warning configuration.approved_drift. ResourceKind=configuration, ResourceID=Asset ID. Agent ID отсутствует: оборудование может быть известно только через Ansible, и backend не выдумывает ему Collector. Контекст включает revision оборудования, эталона и target. Один контекст обновляет один активный инцидент; после закрытия новое отклонение создаёт следующую occurrence.

Более свежий compliant-снимок того же контекста закрывает именно этот drift-инцидент. Это означает совпадение конфигурации с утверждённым эталоном, а не восстановление CPU/SIP/сервиса. Смена эталона, retargeting, неизвестное состояние или отсутствие новых данных не закрывают старый инцидент. Его EvidenceStatus становится stale/missing; закрытие устаревших контекстов оператором отдельным workflow в этот этап не входит.

Проекция идёт по текущему состоянию. Если несколько результатов пришли до прохода worker, обрабатывается последний: это не полный журнал кратковременных drift-эпизодов. Исходная история сравнений сохраняется. Результаты с одинаковым или более старым observed_at не продвигают состояние и не подтверждают восстановление.

## Данные и API

GET /api/incidents?resource_kind=configuration&resource_id=<asset_id> и обычные detail/evidence/transitions/acknowledge доступны с прежними ролями. Отчёты принимают тот же resource_kind. OpenAPI 0.40.0 добавляет signal.configuration: Asset/revision, baseline/target revision, result_id, snapshot_id, normalizer, total_changes, truncated. Текст конфигурации, IP подключения, credentials и diff lines в этот объект не копируются. Подробности сравнения доступны через существующий B11 API.

Сигнал входит в normalized_signals с category=configuration и явной привязкой к Asset. Качество времени estimated: синхронизация часов Ansible Worker отдельно не доказана. Общая корреляция может связать его с другими свежими сигналами того же оборудования или проверенных зависимостей. Такое совпадение не доказывает причину сбоя.

Migration 041 добавляет допустимый тип configuration, durable pending и cursor обработанного результата; старые миграции не изменяются. При ошибке проекции вся страница откатывается: сравнение остаётся в истории, очередь — для повторной попытки. Порядок блокировок Asset → pending совпадает с producer; изменения baseline/target не могут незаметно сменить контекст в ходе обработки.

B12 ещё открыт: topology producer, оставшиеся pattern rules и общая командная приёмка. B13–B16 остаются следующими этапами.
