# Этап 8A — идентичность Agent и основа выпуска сертификатов

Это историческое описание первого шага. Продолжение уже реализовано:
[этап8 — enrollment, renewal и отзыв](stage8-pki.md). Перечень оставшейся PKI
работы ниже относится к состоянию этапа8A, а не текущему архиву этапа8.

## Что исправлено

Ранее TLS подтверждал, что сертификат подписан доверенным CA, но Controller не
сопоставлял владельца сертификата с `agent_id` в AgentHello. Теперь при настройке
`TLS_CLIENT_CA_FILE` backend обязательно выполняет такую проверку. Сертификат
агента A больше не разрешает зарегистрировать агента B.

Проверка включается автоматически в cmd/server, вместе с существующим mTLS.
Новых переменных окружения на этом шаге нет. Обычный локальный insecure режим
сохраняет прежнее поведение. TLS только с серверным сертификатом без client CA
также не выдаёт себя за аутентификацию Agent.

## Подключение по шагам

1. TLS проверяет подпись клиентского сертификата и доверенную цепочку CA.
2. Controller принимает первое AgentHello и проверяет его структуру.
3. Backend получает сертификат из реального gRPC TLS peer, из VerifiedChains.
   Заголовки HTTP и неподтверждённый PeerCertificates не заменяют эту проверку.
4. `agent_id` должен быть UUID в каноническом нижнем регистре, не nil UUID.
   В сертификате должен быть ровно один URI:
   `spiffe://infrapulse/agent/<agent_id>` — ровно как в текущем Agent.
5. Только после успеха backend сохраняет регистрацию и отвечает HelloAck.
6. При каждом следующем сообщении повторно проверяются идентичность и срок
   действия сертификата. Истёкший сертификат не может продолжать запись данных
   через давно открытое соединение.
7. Перед отправкой команды проверяется сертификат той же активной сессии.
   При отказе команда не передаётся в транспорт; Controller закрывает stream.

Ошибка возвращается как gRPC Unauthenticated, без раскрытия внутренних причин
проверки и содержимого сертификата. Для смены UUID необходим сертификат с новым
URI; одного редактирования YAML недостаточно.

## Внутренний issuer

Пакет internal/pki принимает CA certificate/key, проверяет соответствие ключа,
признак CA, право подписывать сертификаты, срок действия и совместимость CA
с client authentication. TTL клиентского сертификата ограничен 1 минутой —
90 сутками; короткое значение предназначено для тестов. Этот конструктор пока
не вызывается production server: публичного endpoint выпуска ещё нет.

Issuer принимает подписанный CSR текущего Agent: PEM CERTIFICATE REQUEST,
ECDSA P-256, ровно один соответствующий URI. Повреждённая подпись, лишние DNS/IP/
email SAN, другой UUID, дополнительные PEM блоки и CSR больше 32 KiB отклоняются.

Сертификат получает только DigitalSignature и ClientAuth. Backend не копирует
запрошенные Subject/Extensions/права CA. Срок не превышает срок issuing CA.
Каждый выпуск получает новый случайный serial и SHA-256 fingerprint. Ответ
совместим с Agent: JSON поля certificate и ca — base64 PEM bytes. Метаданные
issuer не попадают в этот JSON. Закрытый ключ Agent остаётся на стороне Agent.

## Проверки

Unit tests проверяют валидную цепочку ClientAuth, отказ ServerAuth, защиту от
запрошенных прав CA, формат ответа, UUID, подпись CSR, дополнительные SAN,
ограничения размеров/TTL, near-expired CA и ограничение срока сертификата.

Controller tests проверяют отсутствие записи Hello при отказе, отсутствие
сохранения heartbeat после потери авторизации и отсутствие отправки команды.
Отдельный тест поднимает настоящий gRPC с TLS на loopback: доверенный сертификат
агента A не проходит с UUID B; с UUID A приходит успешный HelloAck. Сертификаты
создаются в памяти для теста, закрытые ключи не входят в архив проекта.

Полный прогон с отдельным PostgreSQL и неизменённым Agent проверяет сохранение
предыдущих сценариев SIP, команд и rollback. Он не подтверждает production
enrollment/renewal: их HTTP сервис на этом шаге ещё не создан.

## Что осталось в пункте PKI

- HTTPS `/enroll` и `/renew` в формате существующего Agent.
- Одноразовые UUID-bound bootstrap tokens с хешами и сроком действия в БД.
- Атомарное погашение токена и регистрация сертификата, защита повторных запросов.
- Registry сертификатов, административный выпуск токенов, отзыв и audit.
- Проверка статуса отзыва при подключении/работе Agent, тест обновления сертификата.
- Инструкция создания/размещения CA и server credentials без ключей в GitHub.

До этих шагов считать production PKI завершённым нельзя. Из десяти исходных
пунктов завершены семь; этот архив содержит дополнительную первую часть восьмого
этапа. Live ConfigUpdate требует расширения контракта владельцем Agent;
incidents/reports/AI также остаются отдельной работой.
